01 · positioning

产品定位

先讲清楚这不是什么、是什么、为什么有差异化。这一章是后面所有功能取舍的基准。

1.1不是中台，是 Brand OS

「设计中台」这个词容易让人联想到「批量出图工厂」。我们做的不是这个。viaim Brand OS 的本质是：把品牌系统从 Figma / PDF 这种人类可读、机器难解析的形态，迁移到一个机器可读、可版本化、可被多种生成管线消费的源（Source of Truth）。这个源加上产品资产，加上生成层，构成一个 Brand Operating System。

它和 viaim 主产品「Memory OS」是同构的——都是把分散的资产收敛到一个语义层，让下游应用按需调用。一个管「记忆」，一个管「品牌」，方法论一致。

1.2解决什么痛点

当前 viaim 设计交付存在三个核心问题：

  1. 设计品牌难统一。同一品牌在不同沟通文档、Figma 库、第三方乙方手里漂移。新设计师上手要「问一圈」才知道色值是什么、留白多少。
  2. 大量重复劳动。每个高频物料（社交卡、详情图、PRD 排版）每次都从零开始。3D 渲染图、产品资产散落在各人电脑里，难复用。
  3. AI 工具效果不佳。直接用 Lovart / 通用图像 API 出图，要么风格漂移、要么不像 Aura/Mate、要么文字渲染翻车。设计师宁愿手画。

1.3差异化锚点

市面上没有任何单一产品满足完整需求。三类竞品，各有缺口：

竞品类型代表解决了什么缺口
通用 AI 设计 Lovart · Recraft · Krea 精致度、模型路由、prompt 工程 不知道你的品牌是什么。无法掌握 Aura/Mate 的官方资产、品牌色板、设计禁忌
开源 design-md 工具 Open Design · Open CoDesign DESIGN.md schema · skill 协议 · prompt stack 没有 DAM、没有可视化后台、不做位图生成。只能产出 HTML/Markdown 类「网页设计」
传统 DAM Pimcore · ResourceSpace · AtroDAM 资产仓库、权限、版本控制 没有品牌 DNA、没有 AI 生成、对 LLM 不友好。是仓库不是中台
差异化定位

Lovart 是「让所有人能生成精致图」，Brand OS 是「让 viaim 品牌的图永远是 viaim 的样子」。

不在「精致度」上跟通用工具比拼，而是在品牌还原度 + 资产复用 + 工作流嵌入上做到任何通用产品都不可能做到的事——因为它们不可能掌握 viaim 的内部资产。

1.4v0.1 范围声明

本 PRD 仅覆盖 Phase 1（4-6 周）的内部工具版本，目标用户是 viaim 设计部 + 部分 PM。Phase 2-4 仅在 §9 Roadmap 中给出方向，不展开实现细节。「产品化对外 SaaS」明确不在 v0.1 范围。

03 · form decision

产品形态决策

在三个候选形态中（Brand Console / Studio Canvas / Intent Launcher），评审已选定方案 A · 管控优先（Brand Console），并将 cmd+K 命令面板提升为 P0。

3.1选择 Brand Console 的理由

Brand Console 形态最契合三件事：

  1. 用户优先级匹配。设计师 + 非设计角色 + agency 三类用户都需要"按模块清晰分类"的入口。Studio Canvas（B）会把 PM 吓退；Intent Launcher（C）会让设计师缺乏控制感。Brand Console 是三方共识。
  2. 治理需求强。品牌资产需要版本、审批、合规 lint 的全流程治理。这件事在画布形态（B）里只能是侧边面板，在 launcher 形态（C）里压根没位置。Brand Console 天生为治理而生。
  3. 未来产品化潜力。SaaS 产品大多是 Brand Console 形态（Linear / Pimcore / Brand.ai）。从这里出发未来 Phase 4-5 产品化阻力最小。

3.2cmd+K 命令面板：P0 必做

用户偏好键盘操作（macOS 重度用户）。但「快捷键」有两种产品哲学：

  1. Launcher-as-primary（Raycast 派）：召唤即应用，无状态。不适合长会话场景。
  2. Palette-on-top（Linear / Notion / Figma 派）：完整有状态应用，但任何地方按 ⌘ K 召唤搜索/命令面板。键盘党全程不碰鼠标，鼠标党也能用。

v0.1 选择第二种。Brand Console 是主体，cmd+K 是无处不在的加速器。这个决策把 Command Palette 从「以后再加」提升到 Phase 1 P0 模块，单独立章（§5.5）设计。

3.3Hybrid Path 演进

v0.1 不一次性把所有形态做满。三种形态可以分阶段组合：

5.1.3 版本控制

brand 实例采用语义化版本（v1.0 / v1.1 / v1.2-draft）。每次"发布"创建快照，下游产物记录引用版本。修改流程：编辑 → 草案 → 影响分析 → 审批 → 发布。已发布的版本不可改，只能 deprecate。

5.1.4 与 Markdown 仓库的双向同步

UI 是写入端，Markdown 仓库是物化视图。所有写操作通过 API → 同时写 DB 和 commit MD 到内部 Git 仓。外部允许读 MD（给 agency / Vitana 用），但写操作只能通过 UI/API。这避免了"双向同步地狱"。

5.1.5 v0.1 边界

  • 仅支持单 brand（viaim 主品牌）。多 brand 切换器架构预埋，但 UI 不暴露
  • 仅支持人工编辑。"从 Figma 提取 tokens" 推迟到 Phase 2
  • v0.1.0-0.1.7 含 9 段；v0.1.8 起扩展为 10 段（§10 Users）

5.3.1 四档产物（按 AI 自主度排序）

产物形态

工程级 prompt 字符串。可复制到 Midjourney / Stable Diffusion / Claude / ChatGPT 使用。

谁来收尾

人类设计师。Brand OS 只提供组装好的高质量 prompt，不做生成。

v0.1 边界

P0 必做。是杠杆最高的产物：边际成本极低（一次 LLM 调用），价值很高（让设计师不再"裸 prompt 跑 Midjourney"）。

产物形态

结构化 Markdown 文件（约 1-3 KB），包含项目信息 + brand 摘要 + tokens 子集 + 参考资产 URL。

谁来收尾

下游 AI agent（如 Claude Code、Cursor、Vitana 内部 agent）或外部 agency 的设计师。

核心组装逻辑

用户输入：项目名 / 场景类型 / 调性 / 时长 / 关键产品。系统输出：完整 design brief，下游 AI 读了之后能直接产出符合品牌的设计草图。

v0.1 边界

P0 必做。是 viaim 与 agency 的协作粘合剂——agency 拿这份 MD，自己用 AI 出初稿，避免反复"问 viaim 你们品牌色到底是什么"。

产物形态

可直接交付的合规设计图（PNG / SVG / Figma 文件）。基于预定义模板 + 槽位填充。

谁来收尾

半自动。多数情况下 PM/运营可直接用，复杂场景设计师在 Figma 中精修。

核心组装逻辑

用户选模板（"社交卡 1080" / "PRD 封面" / "活动 banner"）→ 槽位填充（文案 / 选中产品资产 / 自定义颜色）→ 实时渲染 → 合规 lint → 导出。

v0.1 边界

P0 必做但范围小。v0.1 只覆盖 3 个高频模板：社交卡 1080×1080 · 文档/PRD 封面 · 活动 banner 16:9。Phase 2 扩展到 8-10 个模板。

实现路径

Fork Open Design 的 skill 协议作为模板格式（19 个开箱模板可作为参考）。模板用 HTML/SVG 渲染，避开 diffusion 模型的不稳定性，品牌一致性更可控。

产物形态

端到端图像生成。不是「让所有人能生成精致图」，而是「让 viaim 品牌的图永远是 viaim 的样子」。

谁来收尾

设计师做最终选择。L4 输出 4 张候选 + 自动评分排序。

六层管线（已在前期讨论中拍板）
  1. Prompt Rewriter — Claude 重写用户简单描述为工程级 prompt（注入 brand context）
  2. Reference Injection — 自动从 Asset Library 检索匹配资产作为 IP-Adapter / Style ref
  3. Model Router — 按场景路由（gpt-image-2 写实 / Ideogram 文字密集 / Flux 插画）
  4. 参数预设 — 每个场景模板预设最优参数（用户不感知）
  5. 后处理流水线 — 合规 lint + 超分 + 抠图 + 文字层叠加 + 色彩校正
  6. 候选筛选 — 一次跑 4 张，CLIP 相似度 + 美学分 + 合规分加权排序
v0.1 边界

不在 v0.1。L4 推迟到 Phase 3 单独立项（6-8 周，2 工程师）。理由：投入产出比与 v0.1 目标不匹配；L1/L2/L3 已能解决 80% 高频场景。

v0.1 仅保留

L4 tab 在 Studio 中显示为「敬请期待」占位 + roadmap 链接。让用户感知到完整产品形态，但避免误用未成熟功能。

5.3.2 共享上下文构建器（核心 UX 杠杆）

无论 L1-L4 哪一档，用户进入 Studio 第一步是「选场景」。选完场景后：

  • 系统自动注入：当前 brand version 的 tokens / voice / 视觉规范
  • 系统自动检索：Asset Library 中最相关的产品资产（默认 top 3，可换）
  • 系统预填：场景对应的尺寸、构图建议、文案字数上限
  • 用户只填：核心文案 / 关键产品 / 调性微调

这一步把"用户应该输入什么"的决策从用户身上转移到了系统身上，是降低非设计角色门槛的关键。

5.3.3 历史归档与审计

5.11.4 LLM 结构化分析协议

每条 source 调用一次 LLM，使用 system prompt 强约束的 JSON 输出：

{
  "type": "spec | library | article | tool | other",
  "summary": "中文 1-2 句话",
  "brand_sections": ["typography", "voice"],   # 9 段中的 1-3 段
  "key_takeaways": ["3-6 条原子级要点"],
  "applicable_rules": [
    {
      "section": "typography",
      "rule": "中文段落首行缩进 2 字符",
      "rationale": "W3C clreq 推荐",
      "confidence": "high | medium | low"
    }
  ],
  "suggested_brand_updates": [          # 0-5 条具体 schema patch
    {
      "path": "typography.cn_rules",    # dotted path
      "operation": "set | append | merge",
      "value": "...",
      "reason": "为什么这条值得加"
    }
  ],
  "risk_or_caveats": "风险 / 与现有规则冲突 / 版权等"
}

合规约束：返回严格 JSON、无 markdown 围栏、中文 summary、提议的 path 优先用现有 9 段已有字段，新字段允许但要可解释。

5.11.5 应用到 Brand Source · patch 合并

用户在分析结果页勾选要采纳的 patch，点 「→ 合并到 Brand Source 草案」：

  1. 系统调用 Store.ensureDraft() 拿当前 draft（不存在则基于最新 published 创建）
  2. 对每个勾选的 patch 调用 applyPatchToObject(draft.data, patch)，按 operation 决定 set / append / merge 行为
  3. 把变更原因合并到 draft.change_note（含 source 链接）
  4. 在 source 记录 applied_to[] 写入「应用到 vX.Y.Z 哪些段」的痕迹，实现可溯源
  5. UI 跳回 Brand Source，对应 section 即可见新值；用户审阅后正常 publish 走标准 §5.1.3 流程

5.11.6 v0.1.5 边界

  • 仅单 brand 范围。Phase 4 多 brand 时，source 也需要 workspace_id 隔离（schema 已预埋）
  • Jina Reader 是默认抓取代理（免鉴权 / CORS 友好 / 返回 Markdown），可在 Settings 改成自建代理
  • 未实现：定期重新抓取（监测源更新）、来自 RSS 的批量入库 → Phase 2
  • 未实现：自动从 Asset Library 反向归档（让生成产物也能成为 inspiration）→ Phase 3
为什么这是关键基础设施

v0.1 之前 Brand Source 只能从空白手填。有了 Inspiration Pool 之后，brand 升级可以是「读到一篇好文章 → 30 秒入库 → 1 分钟 LLM 分析 → 勾选合并 → 创建 v1.3 草案」的连续路径。这把 brand evolution 从「凭记忆 + 凭印象」变成「有据可查 + 有据可溯」。
